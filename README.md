# papernote

每周跟踪人工智能安全、移动与物联网安全、身份与隐私、软件与应用安全、
系统与硬件安全、网络与通信安全方向的新论文，保存结构化摘要、检索记录和去重索引。

## 内容

- `weekly/`：按周发布的中文论文动态汇总。
- `papers/index.jsonl`：论文主索引，用 DOI、arXiv ID、正式出版链接和规范化标题去重。
- `papers/watchlist.jsonl`：内部待检索清单；记录后续周次需要核验的候选论文，不参与网页构建。
- `papers/academic_graph.json`：由已收录论文生成的单位、学者、合作边和年度顶会计数；会公开到网页。
- `papers/topic_taxonomy.json`：版本化的主领域与细分标签受控词表。
- `papers/entity_registry.json`：单位与学者的稳定 ID、规范显示名和别名。
- `inquiries/`：用户实际提出的具体论文内容问询与讨论；不保存 AI 自动生成的候选/补全文单、任务运行、网站改造或实体审计记录。
- `industry/viewpoints.json`：行业文章与综述的观点摘要。
- `industry/sources.json`：长期扫描的安全研究、威胁情报、模型机构、标准组织和咨询来源池。
- `scripts/build_site.py`：从论文索引、周报和行业观点生成网页数据。
- `site/`：可浏览学术论文、学术关系和行业观点的静态网页。
- `templates/`：周报与问询模板。

## 网页

公开页面：<https://wyinleo.github.io/papernote/>

网页顶部按“学术论文、学术关系、行业观点”区分内容类型；学术论文内部再按周或主领域
浏览。网页不依赖前端框架。更新周报、索引、分类表、名称表或行业观点后，可先校验再
重新生成页面数据：

```bash
python3 scripts/build_site.py --check
python3 scripts/build_site.py
python3 -m http.server 8000 -d site
```

随后访问 <http://localhost:8000>。推送到 `main` 后，GitHub Actions 会重新生成
`site/data.js` 并自动发布 `site/` 到 GitHub Pages。

网页的“学术关系”视图按 CCF 学科口径展示“网络与信息安全”“软件工程与系统”
“人工智能”，并展示单位排行、学者列表和跨单位合作网络。学者姓名在论文卡片、论文
精读、单位关联学者和排行中作为统一入口；点击后以弹层显示规范姓名、论文署名、当前
单位、库内论文数量、可核验主页和最近三篇入库论文。论文与学者详情共用一个弹层和
去重后的返回历史，类型切换时替换当前内容，不创建嵌套弹层，避免循环打开。当前分数
只统计 papernote 已核验并具有结构化单位信息的正式接收论文，是“已核验下界”，不是
单位完整年度产出或通用学术排名。关系分数只用于安排后续检索优先级，不能替代对论文
方法、实验和安全相关性的评价。

## 收录优先级

1. 网络与信息安全领域：优先 IEEE S&P、USENIX Security、ACM CCS、NDSS。
2. 软件工程 CCF-A 会议及其安全相关论文。
3. AI 领域 CCF-A 会议中的智能体安全、模型与系统安全论文。
4. arXiv 预印本：优先知名研究团队、学术或产业实验室以及有代表性作者；统一标为“预印”，表示尚未经过同行评审。

每周报告应优先质量而非数量。仓库不把引用量、作者知名度或单位名气当作论文质量的替代指标。

“本周动态”按本期新发现、新接收、实质更新或值得补齐的历史基线理解，不只限于最近
七天首次公开。补录旧论文时必须保留原始公开时间，并明确标为基线补录，不能误写成
本周首次发布。

## 周报字段规范

每篇论文固定使用以下顺序，字段名称不自行变更：

1. `方向`：从人工智能安全、移动与物联网安全、身份与隐私、软件与应用安全、
   系统与硬件安全、网络与通信安全中选择一个主领域，可补充一个细分方向。
2. `关键词`：紧接方向列出 3—5 个检索与主题关键词。
3. `单位与作者`：先列单位，再列该单位作者；多单位逐行列举，不把全部单位和作者混写
   在同一句中。中国单位使用官方中文全称；中国学者只有在学校主页、个人主页或其他
   权威来源能核验中文姓名时才使用中文，不凭拼音猜字。非中文单位和学者保留官方
   拉丁字母名称，不自行翻译。
4. `出处与状态`：固定写为“文献位置｜状态”，文献位置只写会议或 arXiv；状态只使用“预印”或“接收”，其中 arXiv 一律视为“预印”。
5. `公开或更新时间`：记录可核验的公开或实质更新时间。
6. `原文链接`：提供会议官方原文、作者原文或 arXiv 原文，不再使用“标识符”字段。
7. `核心问题`：用一段完整描述交代研究背景、现有缺口和论文要解决的问题，避免只有一句抽象概括。
8. `方法与贡献`：概述研究设计、关键机制和主要贡献。
9. `方法示例`：结合论文中的案例或按论文方法构造一个简明例子，说明问题如何出现、方法如何处理；若例子由整理者归纳，应避免写成论文原有实验事实。
10. `实验与证据`：记录数据集、对象、指标和主要结果。
11. `局限与风险`：说明证据边界和外推风险。
12. `实践关系`：说明对工程、产品或防御工作的意义。
13. `推荐理由`：解释为何值得阅读。

正文以中文为主。论文标题、作者姓名、会议名称、产品名称以及确有必要的通行缩写可保留英文；其余术语优先采用准确、自然的中文表达，不增设额外的边界说明字段。

## 主题分类

`papers/topic_taxonomy.json` 是 papernote 长期维护的受控分类表，参考 ACM Computing
Classification System、IEEE Taxonomy 和 CCF 学科目录，但按本站的安全研究范围维护。

- 每篇论文只能有一个主领域；交叉研究通过多个细分标签表达。
- 细分标签分为研究对象、安全问题、研究方法和成果类型，不把不同维度混在同一层。
- 新标签必须先写入分类表并给出中文显示名和维度，再写入论文索引。
- 主领域无法由受控规则唯一确定时，必须增加显式覆盖；构建程序不会按规则顺序静默选择。
- 分类表有版本号；合并、改名或废弃标签时保留迁移关系，避免历史条目失去一致性。

## 去重规则

按以下顺序匹配：DOI → arXiv ID → 正式论文 URL → 规范化标题。预印本后续正式发表时，更新原条目并链接两个版本，不新增重复记录。

## 待检索清单

`papers/watchlist.jsonl` 每行保存一个候选论文对象。每周检索应优先处理 `target_week`
不晚于本期的条目：核验原文、发表状态、安全相关性和证据质量。正式收录后写入
`papers/index.jsonl` 并从清单移除；暂缓或不收录时保留条目，并更新 `status`、
`last_checked` 和 `decision_note`。该清单是内部工作队列，不由
`scripts/build_site.py` 读取，也不发布到 GitHub Pages。

## 学术关系库

运行 `python3 scripts/build_site.py` 时，会从论文索引和周报中的结构化“单位与作者”
字段重建 `papers/academic_graph.json`，并同步进 `site/data.js`。关系库包含：

- 论文—作者—单位的归属关系；
- 同一论文产生的跨单位合作边和库内合作次数；
- 单位与学者按年度在网络与信息安全、软件工程与系统、人工智能领域
  CCF-A 会议中的已核验接收论文数；
- 每位学者的规范姓名、论文署名、单位、可核验主页、库内论文数和最近三篇入库论文；
- 数据覆盖范围和计分口径。

旧周报中无法可靠解析的“作者与单位”自由文本不会强行进入图谱。后续精读时应优先
把单位信息整理为当前的“单位：作者”格式，逐步扩大覆盖。

关系库使用 `papers/entity_registry.json` 的稳定实体 ID。落库前必须校验单位是否已经
登记、作者是否能与论文署名匹配、别名是否归并。学者登记项可维护 `display_name`、
`publication_name`、`homepage` 和 `source`；主页与中文名优先从学校官方页、个人主页
和可明确对应本人的 GitHub 主页交叉核验，也可用“大学 + 论文标题/作者”检索新闻或团队
页面。无法可靠对应时保留论文英文署名，不按拼音猜字；未登记单位会使构建失败，避免
错误关系静默公开。

学术关系的数据流固定为：

`papers/index.jsonl` + `weekly/` → `scripts/build_site.py` 校验名称与归属 →
`papers/academic_graph.json` → `site/data.js` → 单位网络、排行和学者卡片。
`academic_graph.json` 与 `site/data.js` 均为生成物，不手工维护；实体纠错应修改
`papers/entity_registry.json`，论文事实应修改主索引或周报，再重新构建。

## 行业观点

行业观点不做普通资讯聚合。每周扫描 `industry/sources.json` 中的固定来源池，通常精选
2—5 篇有原创方法、数据、事件证据、漏洞细节或可复用工程经验的公开内容。纯营销软文、
无方法说明的预测、二手转述和无法访问正文的内容默认排除。

每条观点除摘要和重点外，还必须记录来源类型、内容类型、证据基础、局限与商业利益相关。
厂商或咨询机构的主张不能直接当作独立事实；有条件时应链接底层报告、数据、漏洞公告或
相关论文。付费咨询报告只有在正文或方法说明足以核验时才收录。公开页面中的行业观点
固定按 `published_at` 倒序展示；来源筛选和搜索结果也必须保持最新内容优先。

## 无法核验的论文

若运行环境只能读取题目或摘要、无法稳定取得完整正文，应在当期周报或内部 watchlist
中记录正文缺失及需要核验的证据；不得在 `inquiries/` 中自动生成补全文单。用户补充 PDF
后再精读；在此之前不根据题目、摘要或作者自述补全方法和实验。

只有用户实际发起的论文内容讨论才写入 `inquiries/`，并使用 `templates/inquiry.md` 的统一
格式。AI 自动生成的候选、待下载/待补正文清单和推测性问题，以及检索过程、自动化运行、
站点结构、名称核验和发布状态等内容均不进入。

稿件页眉、作者评论或未生效 DOI 即使写有会议名称，也不单独构成正式接收证据。会议
官方程序不可访问且 DOI 尚未注册时，条目继续按 arXiv“预印”保存，并在当期周报或内部
watchlist 中记录待核验来源；正式来源恢复后更新原索引和原周报卡片，不新增重复条目。

## 任务讨论固化

每次自动化结束前，应整理本次聊天中影响后续运行的检索口径、筛选边界、数据结构、
核验失败处理和发布流程，并同步更新自动化计划卡；同时把适合仓库协作的稳定规则写入
本 README 或相应模板。只固化可复用规则，不把临时故障或一次性内容扩大成长期要求。
