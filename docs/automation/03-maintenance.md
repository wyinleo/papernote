# 第三阶段：数据维护、网站构建与发布

## 阶段目标

对第二阶段写入的数据和历史存量执行事实回查、实体维护、关系图重建、网站校验与发布。本阶段是本次运行的质量门，也是唯一允许生成站点数据、提交和推送的阶段。

## 开始前读取

- `papers/entity_registry.json`（必须完整读取）
- `papers/topic_taxonomy.json`
- `papers/index.jsonl`
- 本期和发生状态变化的历史周报
- 当期 inquiries
- `scripts/build_site.py`
- `.github/workflows/pages.yml`

再次检查 Git 状态，区分运行前用户改动与本次任务改动。

## 历史论文状态回查

- 遍历索引中的预印、仅有 arXiv、待核验或长期未更新条目，核查正式接收、正式出版、DOI、新版本或其他实质更新。
- 优先会议官方论文列表或论文集、DOI 页面和作者公开原文。作者自述不能单独证明正式接收。
- 预印本正式发表时更新原索引条目，不新增重复项，并同步更新原周报卡片的状态、版本时间线、链接、作者单位和受影响的精读内容。
- 本期周报列出历史状态变化；没有变化时明确说明未发现需要升级状态的历史条目。

## 作者、单位与学术关系

- 每次同步维护论文—作者—单位—合作边。页面学科领域固定显示“网络与信息安全、软件工程与系统、人工智能”；“软件工程与系统”只是页面简化名称，不改变现行 CCF-A 检索和计分会议范围。
- 中国单位使用官方中文全称；香港单位可按官方页面保留繁体；其他单位和学者保留官方拉丁字母名称。
- 中国学者仅在英文署名与本人一一对应后使用中文名，不凭拼音猜字。中文名和主页按以下顺序检索：学校官方个人页或成员页、学者个人主页、能明确对应单位、论文和本人的 GitHub。必要时组合检索大学、英文姓名和论文标题，并查学校新闻或团队论文页。
- 学者实体必须维护稳定 `id`、`display_name`、`publication_name`、`language`；找到可靠主页时维护 `homepage`，并用 `source` 保存名称或主页的核验来源。重音符号、括号昵称和中英文名等别名必须归并。
- 新单位必须先用可靠来源登记。“单位与作者”的作者必须能与论文作者列表匹配。仍有歧义时保留英文并写入当期 inquiries，不做猜测。
- 每位入图学者必须有可打开的详情卡片，包含姓名、论文署名、当前单位、库内论文数量、已核验主页、已核验分数和最近入库论文；最近论文最多 3 条。
- 按年度统计安全、软件工程和人工智能三类现行 CCF-A 会议中由正式来源核验为接收的论文数。分数必须标为“已核验下界”，只用于检索优先级，不声称是完整产出或通用排名。

## 数据与前端边界

- 论文事实修正在 `papers/index.jsonl` 或周报，实体修正在 `papers/entity_registry.json`，主题修正在 `papers/topic_taxonomy.json`。不得直接修改 `papers/academic_graph.json` 或 `site/data.js`。
- `scripts/build_site.py` 必须从索引、周报、分类表和实体表校验并重建 `papers/academic_graph.json`，再同步生成 `site/data.js`。
- 网站顶部保持“学术论文、学术关系、行业观点”三个同级内容类型；学术论文内部按周或主题浏览。`papers/watchlist.jsonl` 只作内部队列，不进入公开数据。
- 主页面论文卡片和“最近”排序不得使用 `first_seen` 或落库时间。正式接收或出版论文优先使用时间线中的“正式发表”日期；已经接收但缺少可核验精确日期时只显示会议年份；预印本使用“预印版本”日期。
- 名词解释只在论文详情弹层中显示，主页面论文卡片不显示。
- 论文作者名、论文精读作者名、单位关联学者和学者排行姓名均可打开学者详情。论文详情与学者详情复用同一个弹层。
- 跨类型点击替换当前内容并维护去重的返回历史；目标已在历史中时回退并截断到该节点，不建立嵌套弹层或重复历史，避免论文—学者—论文循环。
- 学术关系前端从 `academic_graph.json` 的单位、学者、合作边、年度分数和 `recent_papers` 渲染，不另建手工数据源。

## 构建与交互验证

1. 运行 `python3 scripts/build_site.py --check`。失败时修正主题、单位、作者、版本时间或行业观点源数据，不得绕过。
2. 运行 `python3 scripts/build_site.py`，重新生成关系图和站点数据。
3. 核对论文数、缓存精读数、本期条目数、主领域数、行业观点数、关系图覆盖，以及每位学者 `recent_papers` 不超过 3 条。
4. 使用本地网站进行最小交互验证，至少覆盖：
   - 论文作者打开学者详情；
   - 排行姓名打开学者详情；
   - 学者最近论文打开论文详情；
   - 返回按钮恢复前一详情；
   - 论文—学者—同一论文循环不产生第二个弹层或重复历史；
   - 主页面日期、详情名词解释和三类顶部入口显示正确。

## 规则固化、Git 与发布

- 本次讨论产生的长期规则写入其唯一负责的自动化分片。只有访客可见行为变化时才更新根目录 `README.md`；字段模板变化时更新 `templates/weekly.md`；阅读方法变化时更新 `docs/paper-reading-guide.md`。不要把相同规则复制到多个位置。
- 保留 `.github/workflows/pages.yml`。
- 只暂存本次相关文件，创建本地提交。远程和认证可用时推送当前分支；否则保留提交并说明原因。
- 成功推送 `main` 后跟踪 GitHub Pages 工作流，并检查 <https://wyinleo.github.io/papernote/>。失败时记录具体失败步骤，不误报部署成功。

## 最终报告

最终报告必须包括：

- 本期摘要与新增论文；
- 历史论文状态变化，没有变化时明确说明；
- 分类、作者、单位和学术关系覆盖；
- 新增行业观点；
- 待人工补充正文或待核验作者清单；
- 构建和关键交互验证结果；
- commit SHA、推送状态、Pages 工作流与线上页面状态；
- 支撑重要接收状态、作者主页或行业结论的可靠来源。
