# Easycatch

让读者先理解一个熟悉场景里的困难，再顺着因果关系理解论文。重在思路和阅读感，不追求缩写版学术摘要。

## 从论文到故事

1. 用 `papers/index.jsonl` 的稳定 ID 定位论文，读取对应周报中的核心问题、方法、方法示例、实验与证据、局限与风险。新增论文先遵循 `docs/paper-reading-guide.md` 阅读原文；改写已有精读时如实说明依据，不能声称重新读过原文。
2. 提炼一个具体矛盾：原来以为什么可靠，哪个交接或细节使事情发生变化，论文抓住了哪个关键点？调查与基准论文可以围绕人的选择、比较是否公平、观察遗漏来构思，不强套攻击故事。
3. 找到生活中具有相同因果关系的场景，保留对象、行动、信任关系与后果的对应。用户喜欢具体、容易跟随的例子，不要求用“像”起头。根据论文选择人物故事或直接的使用场景，不为每篇强行编故事。
4. 故事可以虚构人物与场景，但不能虚构研究证据。第一段可以直接从人物、行动或用户遇到的问题开始；第二段通过具体对应接回论文，让读者分清场景铺垫与作者实际做过的研究。不要为标明类比而把每篇统一写成“像……”或“想象一下……”。不能把依赖物理接触的攻击类比成无条件远程控制。

## 两段成稿

每篇保持两段纯文本。以能讲清因果为准，不用短字数上限挤掉动机、环境与尝试过程，也不为拉长篇幅添加无关背景。

**第一段：按内容选择叙事方式。**

- **人物故事**适合需要借助类比理解的机制。交代谁想完成什么，处在怎样的环境，为什么第一种办法行不通，后来改变了什么，以及这种改变为何产生结果。人物、环境与情节服务于同一条因果链。可以顺叙，也可以从异常结果回看过程、从发现展开调查或比较两次尝试；不把这些路线硬套成固定模板。人物名字只是可选细节，不能给旧比喻加一个 Bob 就算重写。
- **直接使用场景**适合读者已经熟悉的问题。直接讲用户想做什么、什么时候遇到困难、困难有哪些具体表现。例如 Passkey 从换设备、凭据同步和新设备验证写起即可，无需再转到门卡或旅馆。不要把不同产品当成同一种技术。

句子之间要有行动和原因的承接，避免几句短促画面接一句格言式总结。不要只删除“像”或统一替换为“有一天”。环境细节应解释机制：Bob 听琴时墙厚和噪声解释为何一次听不清，固定练习内容与变化的杂音解释为何重复听有帮助。装饰性风景、夸张悬念不承担这个作用。

**第二段：回到论文的思路。** 对应故事里的矛盾，讲清论文要解决什么、为什么沿这个方向做、关键动作如何起作用。保留该论文独有的切入点，少用术语和方法名，不罗列模块与指标，不机械复述摘要。只有影响理解的前提才自然带入；完整实验数字、局限和风险留在下方精读，不另外堆一段免责声明。

避免“不是……而是……”式表达。让语言有画面，同时保持事实边界：生成的人脸不能称为原始像素还原，猜到主题不等于逐字恢复提问，问卷偏好不等于真实授权。

### 两种写法示例

**带噪观测：人物、动机、阻碍与尝试。**

Bob 每天上班都会经过一位钢琴家的练习室。他很喜欢对方的作品，想知道最近有没有新的编曲，可墙太厚，走廊里又总有人说话，每次只能听清几个片段。后来他发现钢琴家常在固定时间练同一段，便连续几天在门外听一会儿，把录到的片段对齐。每天的杂音不同，反复出现的旋律却相同，他逐渐辨认出了先前听不清的乐句。

接到 AEX-NStep 时，解释反复中断与统计差别如何积累线索。音乐是帮助理解的故事，不能把具体方法说成音频降噪，也不能从这个故事推出论文可精确恢复每一步或任意秘密。

**Passkey：直接讲日常使用。**

用户喜欢用密码管理工具减少记忆密码的负担，也希望 Passkey 能让登录更省事。可切换设备时，事情有时并不顺利：凭据没有同步，新设备无法完成验证，或者不同平台之间的操作让人摸不着头绪。第一次注册和登录很方便，只说明起点顺利；日常使用还包括换手机、换电脑，以及在这些设备之间反复接续。

第二段明确这篇论文研究的是 Passkey，再讲为何跟踪真实用户的后续登录可以回答问题。无需创造一个虚构门禁系统绕远解释，也不要把密码管理工具和 Passkey 混为一谈。

## 保存与校验

唯一正文来源是 `papers/easycatch.json`，不要复制进周报或手改生成文件。顶层 `schema_version` 固定为 1，`papers` 按论文稳定 ID 索引，每项包含：

- `paragraphs`：场景铺垫与论文思路两段纯文本。
- `source_sha256`：精读五个来源字段的摘要。
- `revision`：该篇文本从 1 开始的修订号，每次修改递增。
- `skill_version`：本技能 metadata 中的版本，记录本次采用的规则。

完成逐句核对后，再使用构建器的同一函数计算摘要。示例只输出摘要，不自动覆盖旧记录：

```python
from scripts.build_site import parse_weekly_cache, normalize_title, easycatch_source_hash
cache = parse_weekly_cache()
print(easycatch_source_hash(cache[normalize_title("这里填写索引中的完整论文标题")]))
```

运行 `python3 scripts/build_site.py --check`。它拒绝缺少 Easycatch、段落为空、论文 ID 无效或来源已变更的条目。来源变更时先阅读差异并修订解释，再更新摘要；禁止批量刷新摘要掩盖陈旧内容。通过后运行 `python3 scripts/build_site.py`，抽查详情中的显示与作者链接。Easycatch 仅随单篇详情及按周搜索数据加载。

## 迭代规则

读者指出“看不懂”“比喻误导”“遗漏前提”时，先定位到具体句子和来源证据，再修改对应论文。将能复用于其他论文的经验写回本技能，替换不再适用的规则或例子，并递增 metadata.version；既有论文只有实际复核重写后才更新 skill_version。

每次规则变化选三篇不同研究类型做回归阅读，例如系统攻击、测量调查、方法或基准论文。检查第一段选用了合适的叙事路线，行动之间有清楚的动机与因果，第二段能否具体对应论文思路，有没有把故事误读成实验事实；同时确认精读仍保留完整证据与局限。确认没有同类误导后，再按受影响范围修订其他条目。Git 差异与每篇 revision 保留演化过程，不另外堆积重复指南。
