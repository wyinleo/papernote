## 精选论文

### 1. SoK: Attack and Defense Landscape of Agentic AI Systems

- **方向**：人工智能安全 / 智能体系统化研究
- **关键词**：智能体、威胁建模、工具调用、记忆、多智能体
- **名词解释**：
  - **SoK**：Systematization of Knowledge，即把分散研究按统一维度整理、比较并指出空白，而不是提出单一新攻击。
  - **Agentic AI**：能够规划步骤、保存状态并调用外部工具完成目标的 AI 系统，风险不再只来自模型回答本身。
- **单位与作者**：
  - 加州大学伯克利分校：Juhee Kim、Dawn Song
  - 首尔大学：Juhee Kim
  - University of California, Santa Barbara：Wenbo Guo
- **出处与状态**：USENIX Security 2026｜接收
- **公开或更新时间**：2026-08-12 正式论文集公开（由会前版本更新）
- **原文链接**：[USENIX 官方页面](https://www.usenix.org/conference/usenixsecurity26/presentation/kim-juhee-agentic)、[正式论文集 PDF](https://www.usenix.org/system/files/usenixsecurity26-kim-juhee-agentic.pdf)
- **核心问题**：智能体把模型、记忆、规划器和外部工具连接起来后，攻击可能在多个组件与智能体之间传播。既有研究使用的对象和威胁模型不一致，论文因此尝试建立一套能比较攻击入口、传播路径、影响和防御位置的共同框架。
- **方法与贡献**：作者按智能体组件、攻击者能力、安全目标和生命周期整理已有研究，再把攻击与防御放进同一结构中，说明模型层防护为什么不足以覆盖记忆污染、工具滥用和多智能体传播等系统风险。
- **方法示例**：同一条网页恶意指令可以先影响感知模块，再被写入长期记忆，最后诱导工具执行。框架会分别标注初始入口、跨组件传播和现实操作后果，使读者能判断防御应该放在内容隔离、记忆写入还是工具授权环节。
- **实验与证据**：SoK 的主要价值是分类和综合，而非提出单一攻击或防御并做统一基准实验。
- **局限与风险**：智能体技术演化快，分类体系可能很快需要扩展；“首个全面框架”是作者主张，应结合其纳入标准和遗漏范围评估。
- **实践关系**：可用作智能体威胁建模清单：逐项检查模型输入、记忆、工具、环境和智能体间通信，而不是只做提示注入测试。
- **推荐理由**：适合作为后续周报的概念底座，用来判断新论文究竟覆盖模型、记忆、工具、权限还是多智能体传播层。

### 2. MASLeak: Investigating and Exposing Intellectual Property Leakage Vulnerabilities in Multi-Agent Systems

- **方向**：人工智能安全 / 多智能体知识产权泄漏
- **关键词**：多智能体、黑盒攻击、系统提示、协作拓扑、知识产权
- **名词解释**：
  - **黑盒攻击**：攻击者只能提交输入并观察最终输出，看不到模型、提示和内部智能体之间的通信。
  - **协作拓扑**：多个智能体之间的连接和消息传递结构，例如串行链、层级或并行协作。
- **单位与作者**：
  - 香港科技大學：Liwen Wang、Shuai Wang、Zongjie Li、Zhenlan Ji、Zongyi Lyu、Shing-Chi Cheung
  - 中国人民大学：Wenxuan Wang
  - 嶺南大學：Daoyuan Wu
- **出处与状态**：USENIX Security 2026｜接收
- **公开或更新时间**：2026-08-12 正式论文集公开（由会前版本更新）
- **原文链接**：[USENIX 官方页面](https://www.usenix.org/conference/usenixsecurity26/presentation/wang-liwen)、[正式论文集 PDF](https://www.usenix.org/system/files/usenixsecurity26-wang-liwen.pdf)
- **核心问题**：多智能体平台把代理数量、协作结构、系统提示、任务说明和工具配置当作商业资产隐藏在服务端。论文研究仅能调用公开 API 的用户，是否仍可让泄漏内容穿过内部协作链并出现在最终答案中。
- **方法与贡献**：MASLEAK 借鉴蠕虫传播思路构造恶意查询，使泄漏内容在智能体间被诱导、传播并保留；作者还构建了 810 个合成多智能体应用的数据集，并测试 Coze、CrewAI 等真实系统。
- **方法示例**：攻击查询先要求入口智能体复述自身任务，再把这段内容包装成后续代理必须继续处理的“中间结果”。如果内部代理依次遵循该要求，最终输出就可能同时暴露各代理的提示和它们的连接顺序。
- **实验与证据**：作者报告多数场景下系统提示与任务指令提取成功率平均 87%，系统架构提取成功率 92%。
- **局限与风险**：合成应用与真实生产编排的差距需要进一步审查；成功率依赖攻击目标、输出可观测性与后端模型，不能直接外推到所有 MAS。
- **实践关系**：平台应限制代理间消息可携带的内部配置，区分任务数据与控制指令，并在最终输出前检查系统提示、工具说明和拓扑信息是否被带出。
- **推荐理由**：把“提示泄漏”提升到系统架构与协作协议层，直接关联 Agent 平台的商业机密保护和最小披露设计。

### 3. Network-Level Prompt and Trait Leakage in Local Research Agents

- **方向**：人工智能安全 / 研究智能体网络隐私
- **关键词**：研究智能体、网络侧信道、流量元数据、提示推断、用户画像
- **名词解释**：
  - **网络侧信道**：不读取加密正文，而从访问域名、顺序和时间等伴随信息推断敏感内容。
  - **用户特征推断**：把多个会话的访问模式合并，推测职业、健康关注或兴趣等长期属性。
- **单位与作者**：
  - University of Massachusetts Amherst：Hyejun Jeong、Mohammadreza Teymoorianfard、Abhinav Kumar、Amir Houmansadr、Eugene Bagdasarian
- **出处与状态**：USENIX Security 2026｜接收
- **公开或更新时间**：2026-08-12 正式论文集公开（由会前版本更新）
- **原文链接**：[USENIX 官方页面](https://www.usenix.org/conference/usenixsecurity26/presentation/jeong)、[正式论文集 PDF](https://www.usenix.org/system/files/usenixsecurity26-jeong.pdf)
- **核心问题**：本地运行模型和 TLS 加密只能隐藏内容，研究智能体仍会为一次问题密集访问大量语义相关网站。论文研究 DNS、VPN、代理或网络运营方能否仅凭这些元数据重建用户问题，并从多次研究任务累积个人特征。
- **方法与贡献**：论文构建真实与合成人物查询的流量数据集，并提出 OBELS 指标衡量原始提示与推断提示在功能和领域知识上的相似度。
- **方法示例**：用户查询抑郁症帮助时，观察者看不到提示正文，却能看到智能体连续访问临床试验、精神健康和远程医疗域名。攻击模型把域名与访问顺序组合起来，生成与原任务功能和领域接近的推断提示。
- **实验与证据**：研究智能体每个请求访问约 70—140 个域；作者报告攻击可恢复超过 73% 的提示功能/领域知识，多会话下最多恢复 32 个潜在特征中的 19 个；限制域多样性或混淆流量使攻击效果平均降低 29%，且作者称效用影响很小。
- **局限与风险**：指标与“恢复百分比”不等同于逐字重建；效果对代理策略、缓存、加密 DNS、网络路径和用户行为分布敏感。
- **实践关系**：敏感研究任务不能只依赖本地模型和 TLS；部署时还需考虑域名最小化、代理汇聚、缓存和可接受的流量混淆成本。
- **推荐理由**：对“本地运行即隐私安全”的直觉形成重要反例，也直接影响自动研究、搜索与企业情报智能体的部署架构。

### 4. Bridges to Self: Silent Web-to-App Tracking on Mobile via Localhost

- **方向**：移动与物联网安全 / Web—App 跨域跟踪
- **关键词**：localhost、跨上下文跟踪、Android、WebRTC、隐私隔离
- **名词解释**：
  - **localhost**：设备指向自身的网络地址；网页访问它时可能连接到同一手机上由原生应用开启的服务。
  - **跨上下文跟踪**：把浏览器 Cookie 与原生应用账号或设备标识关联，使两个原本隔离的环境共享用户身份。
- **单位与作者**：
  - COSIC, KU Leuven：Tim Vlummens
  - IMDEA Networks Institute：Aniketh Girish、Nipuna Weerasekara、Narseo Vallina-Rodriguez
  - Radboud University：Frederik Zuiderveen Borgesius、Gunes Acar
- **出处与状态**：USENIX Security 2026｜接收
- **公开或更新时间**：2026-08-12 正式论文集公开（由会前版本更新）
- **原文链接**：[USENIX 官方页面](https://www.usenix.org/conference/usenixsecurity26/presentation/vlummens)、[正式论文集 PDF](https://www.usenix.org/system/files/usenixsecurity26-vlummens.pdf)
- **核心问题**：浏览器按来源隔离网站，Android 也把应用放进独立沙箱，但网页仍可能访问本机网络服务。论文研究广告或分析脚本能否借 localhost 与已登录的原生应用交换标识，从而绕过清 Cookie、无痕模式和应用隔离。
- **方法与贡献**：结合美国和欧盟视角的大规模网页抓取与 Android App 系统分析，刻画 HTTP(S)、WebSocket、WebRTC 等标准被用于跨上下文跟踪的机制，并分析浏览器修复与 Local Network Access 权限方案。
- **方法示例**：网页中的统计脚本向 `localhost` 端口发送浏览器 Cookie；同一手机上的社交应用监听该端口并返回与登录账号关联的标识。网站由此把匿名浏览记录与长期应用身份连接起来。
- **实验与证据**：作者报告 Meta 与 Yandex 曾使用这类桥接；该技术可绕过清 Cookie、无痕模式、广告 ID 重置、VPN 及工作/个人配置隔离，并指出 WebRTC 全局单播 IPv6 和 `.local` mDNS 仍可能形成旁路。
- **局限与风险**：生态修复持续变化，具体可利用性需结合当前浏览器和 App 版本复测；法律分析与技术结论应分开理解。
- **实践关系**：浏览器和移动平台应把网页访问本机地址视为跨边界能力并取得明确授权，应用也不应在无认证本地端口暴露稳定标识。
- **推荐理由**：真实世界影响强，揭示“浏览器沙箱”和“App 沙箱”分别成立时，跨生态组合仍可能破坏隐私边界。

### 5. Cracks in the Walled Garden: Dissecting the Gray-Market of Unauthorized iOS App Distribution via Ad Hoc Sideloading

- **方向**：移动与物联网安全 / iOS 非官方分发
- **关键词**：iOS、Ad Hoc、侧载、签名证书、软件供应链
- **名词解释**：
  - **Ad Hoc provisioning**：苹果允许开发者把应用签给有限设备测试的分发方式，灰产会批量收集设备标识并滥用该渠道。
  - **侧载**：不经过官方应用商店，把应用安装包直接安装到设备上的过程。
- **单位与作者**：
  - 清华大学：Yijing Liu、Yiming Zhang、Baojun Liu、Haixin Duan
  - 北京信息科学与技术国家研究中心：Yijing Liu、Yiming Zhang、Baojun Liu、Haixin Duan
- **出处与状态**：USENIX Security 2026｜接收
- **公开或更新时间**：2026-08-12 正式论文集公开（由会前版本更新）
- **原文链接**：[USENIX 官方页面](https://www.usenix.org/conference/usenixsecurity26/presentation/liu-yijing)、[正式论文集 PDF](https://www.usenix.org/system/files/usenixsecurity26-liu-yijing.pdf)
- **核心问题**：Ad Hoc 原本服务于小规模真机测试，但签名站、证书转售者和改包工具已把它组成绕过 App Store 审核的商业链条。论文研究这条链怎样运作、分发了什么，以及攻击者如何修改正版应用。
- **方法与贡献**：以用户视角收集并分析签名站点、签名工具和 `.ipa` 分发样本，反向工程证书流通与应用修改手法。
- **方法示例**：用户在签名站提交设备标识并购买安装服务；平台用企业控制的开发证书给修改后的 `.ipa` 重签名，其中可能已经注入广告或动态库，随后生成可直接安装的链接。
- **实验与证据**：作者识别 3,359 个活跃签名站点，逆向 12 个签名工具，获得 8,216 个 `.ipa` 条目，并报告证书转售利润率最高达 3,000%；大量样本是注入动态库的正版 App 修改版。
- **局限与风险**：研究重点是中国市场，地域和时间外推需谨慎；样本发现渠道可能遗漏封闭社群，风险类别也不代表每个样本都已被证实恶意。
- **实践关系**：平台治理需要同时处理证书申请、设备注册、签名服务和改包工具，而不能只在发现单个恶意应用后下架样本。
- **推荐理由**：将单个恶意 App 问题扩展到证书、工具、分发站与修改包构成的供应链，适合移动应用风控和平台治理研究。

### 6. The State of Passkeys: Studying the Adoption and Security of Passkeys on the Web

- **方向**：身份与隐私 / Passkey 身份认证
- **关键词**：Passkey、WebAuthn、FIDO2、账户接管、互联网测量
- **名词解释**：
  - **Passkey**：用设备保存的公私钥对替代密码，登录时由设备签名网站发来的随机挑战。
  - **WebAuthn**：浏览器与网站之间注册和使用公钥凭据的标准 API，是 Passkey 登录流程的一部分。
- **单位与作者**：
  - Ruhr University Bochum：Louis Jannett、Vladislav Mladenov、Jörg Schwenk
  - Heilbronn University of Applied Sciences：Andreas Mayer、Maximilian Westers
  - University of Wuppertal：Christian Mainka
- **出处与状态**：USENIX Security 2026｜接收
- **公开或更新时间**：2026-08-12 正式论文集公开（由会前版本更新）
- **原文链接**：[USENIX 官方页面](https://www.usenix.org/conference/usenixsecurity26/presentation/jannett)、[正式论文集 PDF](https://www.usenix.org/system/files/usenixsecurity26-jannett.pdf)
- **核心问题**：Passkey 的密码学设计能抵抗传统钓鱼，但真实网站还要正确处理注册、删除、账户恢复和会话绑定。论文研究网站采用情况，以及这些生命周期操作是否真正遵守 WebAuthn 的安全要求。
- **方法与贡献**：PASSKEYS-RADAR 汇聚社区目录、Tranco、CrUX 和历史网页数据；PASSKEYS-ATTACKER 可操纵 WebAuthn 各阶段消息并实现 15 类攻击测试。
- **方法示例**：攻击工具截获网站发给浏览器的注册参数，替换用户或挑战等字段，再观察服务器是否仍接受返回凭据。若网站只验证签名却没有把操作绑定到当前会话，攻击者可能注册自己的 Passkey 或删除受害者凭据。
- **实验与证据**：作者分析 872 个启用 Passkey 的网站，并在 103 个网站上评估攻击；18 个网站存在两类关键严重度风险，53 个至少存在一类高严重度风险，影响包括账户接管、删除 Passkey、锁定和会话固定。
- **局限与风险**：扫描是时间截面，网站可能已修复；CVSS 严重度和实际可利用条件不完全等价，测试站点也不是全体部署的随机样本。
- **实践关系**：部署 Passkey 时需要测试完整生命周期和会话绑定，不能因为使用了抗钓鱼协议就跳过注册、删除与恢复流程的授权检查。
- **推荐理由**：说明“采用抗钓鱼标准”并不自动等于安全，实现、生命周期管理和恢复流程同样关键。

### 7. Patch-Guided Vulnerability Detection: Extracting Java API Security Rules via Attack–Defense Cross-Analysis

- **方向**：软件与应用安全 / Java API 误用检测
- **关键词**：安全敏感 API、补丁挖掘、静态分析、规则合成、漏洞检测
- **名词解释**：
  - **安全敏感 API**：参数或返回值使用错误时可能导致代码执行、数据泄漏等严重后果的接口。
  - **补丁挖掘**：从漏洞修复前后的代码差异中提取缺失检查、危险调用和修复策略。
- **单位与作者**：
  - 复旦大学：Bofei Chen、Shuang Liao、Lei Zhang、Yuan Zhang
  - EPFL：Chibin Zhang、Mathias Payer
- **出处与状态**：USENIX Security 2026｜接收
- **公开或更新时间**：2026-08-12 正式论文集公开（由会前版本更新）
- **原文链接**：[USENIX 官方页面](https://www.usenix.org/conference/usenixsecurity26/presentation/chen-bofei)、[正式论文集 PDF](https://www.usenix.org/system/files/usenixsecurity26-chen-bofei.pdf)
- **核心问题**：Java API 文档通常只讲正常功能，未必写出安全调用约束；从大量代码中学习“多数写法”又可能把普遍错误当成正确模式。论文研究能否把已经确认的安全补丁转成精确规则，并据此寻找其他项目中的同类误用。
- **方法与贡献**：VulGenie 使用补丁图隔离约束与防御修改，通过攻防交叉验证合成规则，并以偏差引导静态分析扩展检测。
- **方法示例**：某补丁在调用表达式求值 API 前新增对 `eval` 等危险关键字的过滤。系统从差异中识别“缺少输入净化”这一约束，再搜索其他项目里到达同类求值 API、却没有相应检查的数据流。
- **实验与证据**：在 150 个近期 Java 安全补丁上抽取 198 条规则，作者报告精度 81.82%，其中 177 条未被 CodeQL 覆盖；在 10 个流行 Java 应用中发现 46 个零日漏洞，25 个已修复并获分配 10 个 CVE。
- **局限与风险**：评估规模和项目选择影响外部有效性；“CodeQL 未覆盖”不代表 CodeQL 无法通过新规则覆盖，零日确认程度需结合披露与补丁核验。
- **实践关系**：适合把组织积累的漏洞补丁转成可重复扫描规则，并与 CodeQL 等现有规则库互补；自动结果仍需人工确认数据流和可利用条件。
- **推荐理由**：把补丁知识自动转化为可执行检测规则，连接软件工程中的补丁挖掘与应用安全中的可扩展漏洞发现。

### 8. Opossum Attack: Application Layer Desynchronization using Opportunistic TLS

- **方向**：网络与通信安全 / TLS 协议组合
- **关键词**：机会式 TLS、隐式 TLS、协议反同步、中间人、HTTP
- **名词解释**：
  - **机会式 TLS**：连接先以明文协议开始，再通过 `STARTTLS` 或升级命令切换到 TLS。
  - **协议反同步**：通信双方对当前请求与响应属于哪一轮产生不同理解，攻击者因而能把旧响应冒充成新请求结果。
- **单位与作者**：
  - Technology Innovation Institute：Robert Merget
  - Ruhr University Bochum：Nurullah Erinola、Marcel Maehren、Lukas Knittel、Marcus Brinkmann、Jörg Schwenk
  - Paderborn University：Sven Hebrok、Juraj Somorovsky
- **出处与状态**：USENIX Security 2026｜接收
- **公开或更新时间**：2026-08-12 正式论文集公开（由会前版本更新）
- **原文链接**：[USENIX 官方页面](https://www.usenix.org/conference/usenixsecurity26/presentation/merget)、[正式论文集 PDF](https://www.usenix.org/system/files/usenixsecurity26-merget.pdf)
- **核心问题**：旧协议常同时支持“一开始就是 TLS”和“先明文再升级 TLS”两种模式。论文研究即使 TLS 本身正确，中间人能否利用两种状态机对消息边界的不同理解，让客户端把攻击者预先触发的响应误认成自己加密请求的结果。
- **方法与贡献**：论文提出不依赖具体实现 Bug 的应用层反同步攻击，并详细分析 HTTP 的四类利用方向。
- **方法示例**：中间人先在明文连接中发送 `GET /dog` 并请求升级 TLS，再把浏览器的 TLS 握手转发进去。握手后浏览器发送 `GET /cat`，攻击者不转发该请求，服务器随后返回先前 `/dog` 的响应，浏览器却把它当作 `/cat` 的可信 HTTPS 响应。
- **实验与证据**：IPv4 范围扫描发现超过 300 万服务器同时支持相关模式；HTTP 场景中发现 20,121 台服务器在 35 个端口支持机会式 HTTP，其中 2,268 台也支持 HTTPS，539 台使用相同域名，构成作者定义的可利用场景。
- **局限与风险**：暴露面数字不等于已确认成功利用；真实攻击仍依赖网络中间人位置、客户端/服务器行为及部署配置。
- **实践关系**：服务器和客户端应避免在同一逻辑端点混用两种 TLS 启动模式，并在升级时清空未完成请求状态；协议测试还要覆盖状态组合而非只检查密码套件。
- **推荐理由**：提醒工程团队：即使 TLS 算法和实现本身现代且正确，协议组合与状态机语义仍会破坏认证保证。
