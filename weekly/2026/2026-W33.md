### 1. Autonomy Comes with Costs: Detecting Denial-of-Service Vulnerabilities Caused by Resource Abusing in LLM-based Agents

- **方向**：人工智能安全 / 智能体资源治理
- **关键词**：智能体安全、资源耗尽、拒绝服务、定向灰盒模糊测试、资源生命周期
- **名词解释**：
  - **资源生命周期**：文件、进程或云实例从创建到释放的完整过程；智能体若遗漏清理步骤会持续占用资源。
  - **资源耗尽型拒绝服务**：攻击者诱导系统反复创建或保留资源，最终让正常请求无法获得服务。
- **单位与作者**：
  - 复旦大学：Jiaqi Luo、戴嘉润、刘丰毓、Songyang Peng、Youkun Shi、Tong Bu、Geng Hong、Xudong Pan、张源
  - 上海创智学院：Xudong Pan
- **出处与状态**：USENIX Security 2026｜接收
- **公开或更新时间**：2026-08-12 正式发表
- **原文链接**：[USENIX 官方页面](https://www.usenix.org/conference/usenixsecurity26/presentation/luo)、[正式论文集 PDF](https://www.usenix.org/system/files/usenixsecurity26-luo.pdf)
- **核心问题**：智能体能自主下载、解析和保留数据，却常缺少跨单轮、会话和进程生命周期的资源上限。传统模糊测试既不理解自然语言功能语义，也不知道资源应在何时释放，因而容易漏掉渐进累积型拒绝服务。
- **方法与贡献**：AgentDoS 静态识别资源分配、使用与释放点，把资源分为单任务、会话内和全局持久三种生命周期，再由 LLM 生成能到达特定功能且扩大资源消耗的自然语言种子，以定向灰盒反馈迭代触发条件。
- **方法示例**：若下载文件只在任务结束释放，工具生成一次性超大下载提示；若向量、历史或文件句柄跨轮保留，则在同一会话反复调用并监测资源增长，而不是把每轮独立测试。
- **实验与证据**：20 个开源智能体中，工具分析 2,025 个潜在资源操作，生命周期识别准确率 95.2%；在 16 个项目发现 36 个此前未知的 DoS 漏洞，其中 15 个已获 CVE。对含 38 个真值漏洞的比较中，AgentDoS 为 100% 精度、94.7% 召回，AgentFuzz 召回仅 7.9%。
- **局限与风险**：静态分析会漏掉间接调用，作者需人工标定 Web API 入口；两处漏报来自未解析的数据流。评测主要面向 Python 智能体，资源阈值、运行环境与模型价格会影响复现成本，平均每个智能体约 5.95 小时和 932 万 Token。
- **实践关系**：智能体平台应对文件、上下文、向量库、子进程和网络连接同时设置每任务、每会话和全局配额，并让异常终止路径也执行确定性清理；安全测试要覆盖跨轮累积而非只看单次调用。
- **推荐理由**：它把“智能体耗资源”从一般性能问题明确为可复现、可获 CVE 的安全缺陷，并给出生命周期驱动的系统化测试方法。

### 2. When AIOps Become “AI Oops”: Subverting LLM-driven IT Operations via Telemetry Manipulation

- **方向**：人工智能安全 / 智能运维
- **关键词**：AIOps、遥测操纵、间接提示注入、奖励投机、运行时防御
- **名词解释**：
  - **AIOps**：用机器学习或大模型分析监控数据并辅助执行运维操作的系统。
  - **遥测操纵**：攻击者篡改日志、指标或告警，使运维智能体形成错误判断并采取错误动作。
- **单位与作者**：
  - RSAC Labs：Dario Pasquini、Omer Akgul、Athanasios Theocharis、Petros Efstathopoulos
  - George Mason University：Evgenios M. Kornaropoulos、Giuseppe Ateniese
- **出处与状态**：USENIX Security 2026｜接收
- **公开或更新时间**：2026-08-12 正式发表
- **原文链接**：[USENIX 官方页面](https://www.usenix.org/conference/usenixsecurity26/presentation/pasquini)、[正式论文集 PDF](https://www.usenix.org/system/files/usenixsecurity26-pasquini.pdf)
- **核心问题**：LLM 驱动的运维智能体把日志、报错和指标当作诊断事实，并可能自动执行修复。外部攻击者即使没有运维权限，也能通过畸形请求把可控文本写入遥测，诱导智能体采取破坏基础设施完整性的动作。
- **方法与贡献**：AIOpsDoom 以端口扫描和爬取做黑盒侦察，用模糊测试寻找会进入日志的入口，再由 LLM 生成与目标应用相符的“错误解释”，推动智能体选择攻击者期望的修复。AIOpsShield 则根据遥测模板与结构化字段标记不可信参数并在交给模型前净化。
- **方法示例**：攻击者让公开接口产生包含伪造根因和修复建议的错误；AIOps 智能体把这段日志当作系统结论，进而删除健康组件或改变配置。防御端只保留模板语义，把用户可控字段替换为不可信占位符。
- **实验与证据**：作者在 AIOpsLab 的 3 个微服务应用、2 个智能体、GPT-4o 与 GPT-4.1、3 类恶意修复上进行 36 种配置各 5 次，共 180 次试验，平均攻击成功率 90%，最难配置仍为 82.2%；普通提示注入基线为 0。AIOpsShield 对 84、12 和 132 个模板的三应用实验均阻断攻击，12 个故障场景中的任务效用与无防御时相近。
- **局限与风险**：实验应用是隔离的合成微服务，模型裁判只抽取约 10% 由人工复核；模板和正则净化是启发式方案，未结构化日志、供应链输入或新的编码方式可能绕过。约 50% 的正常故障解决率也说明基础智能体能力有限。
- **实践关系**：遥测必须像网页和邮件一样视为攻击者可控输入；自动修复应绑定最小权限、变更审批、可回滚事务与结构化来源标记，不能把“由监控系统产生”误当作可信。
- **推荐理由**：论文把间接提示注入落到真实运维控制面，并同时量化攻击与可部署净化方案，直接关联生产自动化风险。

### 3. PANGOLIN: Fuzzing Multilingual IoT Firmware with LLM-Driven Code Analysis

- **方向**：移动与物联网安全 / 多语言固件
- **关键词**：IoT、固件模糊测试、跨语言代码分析、隐藏接口、LLM Agent
- **名词解释**：
  - **多语言固件**：同一固件同时包含 C/C++、脚本和配置等多种语言，接口关系难以由单一分析器恢复。
  - **隐藏接口**：未在公开文档中说明、但仍能通过网络包或设备输入触发的命令入口。
- **单位与作者**：
  - 中国人民解放军信息工程大学：Zhipeng Jia、Xiaokang Yin、Jiangan Ji、Enzhou Song、Ruijie Cai、Shengli Liu
  - 先进计算与智能工程实验室：Shuitao Gan
  - 清华大学网络科学与网络空间研究院：Chao Zhang
  - 清华大学网络科学与网络空间研究院—科学城（广州）数字科技集团有限公司系统安全联合研究中心：Chao Zhang
  - 数学工程与先进计算国家重点实验室：Hangtian Liu、Jinglei Tan
- **出处与状态**：USENIX Security 2026｜接收
- **公开或更新时间**：2026-08-12 正式发表
- **原文链接**：[USENIX 官方页面](https://www.usenix.org/conference/usenixsecurity26/presentation/jia-zhipeng)、[正式论文集 PDF](https://www.usenix.org/system/files/usenixsecurity26-jia-zhipeng.pdf)
- **核心问题**：路由器等 IoT Web 后端常由 C、Lua、Python 等多种语言共同实现，大量接口不在前端暴露，参数又跨语言解析。依赖网络流量的模糊测试无法得到完整入口和层级参数，单语言静态分析也无法追踪跨语言调用。
- **方法与贡献**：PANGOLIN 用 LLM 识别多级分发机制并建立 URI—处理函数映射，再由 Agent 沿跨语言调用图生成参数规范；运行时响应反馈用于修正幻觉或不完整规范，最终以语义有效请求驱动实体设备模糊测试。
- **方法示例**：前端没有引用的管理 URI 仍会被后端分发表注册。工具先定位分发代码，再从 Lua 表到 C 处理函数追踪嵌套 JSON 参数；若响应提示字段类型错误，就更新规范并重新生成请求，而不是只随机变异抓包种子。
- **实验与证据**：12 台实体设备、8 家厂商上提取 2,856 个接口，其中 1,793 个为隐藏接口；2,253 份参数规范可产生有效请求，有效率 78.89%。工具发现 68 个此前未知漏洞，其中 45 个来自隐藏接口、31 个获漏洞编号；发现数为 LABRADOR 的 2.96 倍，静态提取阶段快 19.1 倍。
- **局限与风险**：设备和厂商样本有限，分发模式仍需扩展；LLM 生成会幻觉，必须依靠代码证据和响应反馈纠正。实体测试依赖特定设备状态与外围配置，已发现漏洞的可达性和影响仍需逐个责任披露确认。
- **实践关系**：IoT 厂商应把未出现在前端的管理接口纳入资产清单和认证测试，并对跨语言边界的参数、权限和错误处理做统一验证；LLM 分析结果不能脱离动态证据直接作为漏洞结论。
- **推荐理由**：它把 LLM 的代码语义能力嵌入可验证的固件测试闭环，并用实体设备、隐藏接口和漏洞编号提供了强证据。

### 4. FirmReBugger: A Benchmark Framework for Monolithic Firmware Fuzzers

- **方向**：系统与硬件安全 / 单体固件评测
- **关键词**：单体固件、模糊测试、漏洞预言机、评测基准、可复现性
- **名词解释**：
  - **单体固件**：应用、驱动和系统逻辑紧密编译在一个映像中的固件，难以拆分后单独测试。
  - **漏洞预言机**：根据崩溃、异常状态或已知触发条件判断一次测试是否真的发现漏洞的规则。
- **单位与作者**：
  - University of Adelaide：Mathew Duong、Michael Chesser、Guy Farrelly、Damith C. Ranasinghe
  - Data61 CSIRO：Surya Nepal
- **出处与状态**：USENIX Security 2026｜接收
- **公开或更新时间**：2026-08-12 正式发表
- **原文链接**：[USENIX 官方页面](https://www.usenix.org/conference/usenixsecurity26/presentation/duong)、[正式论文集 PDF](https://www.usenix.org/system/files/usenixsecurity26-duong.pdf)
- **核心问题**：单体固件模糊测试常用覆盖率和“唯一崩溃”比较工具，但硬件仿真差异会制造不可达状态或重复崩溃，导致指标不公平。领域需要不修改目标二进制、又能精确判断同一真实缺陷是否被触发的基准。
- **方法与贡献**：FirmReBugger 用 C 表达式描述漏洞预言机 Raven，并把 fuzzer 产生的种子在独立解释器中重放，区分未到达、到达、触发和检测四种状态。FirmBench 汇集真实固件二进制、漏洞与硬件交互障碍，并以服务形式统一运行 9 个工具。
- **方法示例**：对越界写，预言机描述“长度超过缓冲区且写路径已到达”，而不是把一次模拟器崩溃当作新漏洞；同一种子脱离 fuzzer 重放，使插桩和判定逻辑不会泄漏给被测工具。
- **实验与证据**：基准包含 61 个二进制、313 个初始预言机，归并为 33 个目标中的 187 个独立真实漏洞，覆盖 34 类 CWE、14 种 MCU 与 10 个系统库。9 个 fuzzer 各 10 次、每次 24 小时，累计约 10 CPU 年；三组实验共 295 个漏洞，工具触发 181 个，Hoedur 与 MultiFuzz 分别触发 150 和 144 个。
- **局限与风险**：目标和漏洞选择仍有偏差，社区扩展可能造成对基准过拟合；部分仿真状态在物理设备上不可能出现，作者保留但显式标注。并非所有 fuzzer 都能运行全部目标，横向总分需要结合适用范围解释。
- **实践关系**：固件测试团队应以可重放漏洞为核心指标，同时报告覆盖、可达性和仿真真实性；采用公开基准时要保留未公开回归集，避免只针对已知预言机调参。
- **推荐理由**：这是一项对整个固件模糊测试评测方法的基础设施工作，能帮助判断新工具究竟发现了更多漏洞，还是只制造了更多崩溃。

### 5. DNS Cache Poisoning Like it’s 2006

- **方向**：网络与通信安全 / DNS
- **关键词**：DNS 缓存投毒、BIND 9、伪随机数状态恢复、源端口预测、TXID
- **名词解释**：
  - **TXID**：DNS 查询与响应中的事务编号，解析器用它把返回包对应到原始请求。
  - **伪随机数状态恢复**：从已观察到的随机输出反推出生成器内部状态，进而预测后续端口或编号。
- **单位与作者**：
  - Hebrew University of Jerusalem：Omer Ben-Simhon、Amit Klein
- **出处与状态**：USENIX Security 2026｜接收
- **公开或更新时间**：2026-08-12 正式发表
- **原文链接**：[USENIX 官方页面](https://www.usenix.org/conference/usenixsecurity26/presentation/ben-simhon)、[正式论文集 PDF](https://www.usenix.org/system/files/usenixsecurity26-ben-simhon.pdf)
- **核心问题**：现代 DNS 缓存投毒同时受到随机 UDP 源端口和 16 位 TXID 保护。论文研究 BIND 9 的 Xoshiro128** 伪随机数状态能否通过客户端可见的 RRset 顺序等输出恢复，从而同时预测两项挑战值。
- **方法与贡献**：作者构造 ANY、RRset 顺序和 QNAME 最小化等原子或近原子查询，从少量输出反推 PRNG 状态；新版本可完全从客户端侧完成，旧 9.18 分支使用攻击者权威服务器辅助。方法还考虑预取、DNS Cookie、转发器、状态防火墙和高查询负载。
- **方法示例**：攻击者向同一解析器查询包含多条记录的域名，观察随机返回顺序并恢复内部状态；随后预测下一次查询的源端口与 TXID，只需很少伪造响应即可赢得与真实权威服务器的竞速。
- **实验与证据**：Azure 隔离环境中的 BIND 9.18.38、9.20.11 与 9.21.10 上，RRset/ANY 变体为 100% 成功，RR-QMA 为 92%—100%。对 5 个开放 BIND 9.20 解析器做受控安全测试，4 个满足条件，3 个在 500 个 PRNG 步内成功。攻击在每秒 1 万查询和状态防火墙条件下仍可工作。
- **局限与风险**：攻击仍需源地址伪造或可控查询，DNSSEC 正确验证会阻断伪造记录；开放解析器实验规模很小，生产测试受伦理限制。ISC 已以 CVE-2025-40780 在 BIND 9.18.41、9.20.15、9.21.14 修复 PRNG，并移除相关随机 RRset 行为，FreeBSD 也修复 CVE-2025-24934，因此不能将论文描述成未修补零日。
- **实践关系**：运营方应升级 BIND 并启用 DNSSEC 验证、响应速率限制和网络出口反欺骗；自研协议不能把非密码学 PRNG 的输出同时复用在可观察随机化和安全挑战值上。
- **推荐理由**：论文用完整状态恢复证明“源端口随机化”若建立在可观测 PRNG 上仍会失效，同时提供了明确补丁版本和长期设计教训。

### 6. DaLens: Charting DNS Self-Amplification Threats at Large

- **方向**：网络与通信安全 / DNS 可用性
- **关键词**：DNS 自放大、开放解析器、互联网测量、拒绝服务、递归拓扑
- **名词解释**：
  - **DNS 自放大**：一个查询在解析器之间形成额外递归或重复请求，使目标系统自己放大工作量。
  - **开放解析器**：允许任意互联网用户提交递归查询的 DNS 服务，容易被滥用为攻击入口。
- **单位与作者**：
  - ETH Zurich：Liwen Xu、Zechao Cai、Adrian Perrig
  - 香港科技大学（广州）：Huayi Duan
- **出处与状态**：USENIX Security 2026｜接收
- **公开或更新时间**：2026-08-12 正式发表
- **原文链接**：[USENIX 官方页面](https://www.usenix.org/conference/usenixsecurity26/presentation/xu-liwen)、[正式论文集 PDF](https://www.usenix.org/system/files/usenixsecurity26-xu-liwen.pdf)
- **核心问题**：DNS 自放大攻击让一个客户端请求诱导递归与权威服务器反复交互，消耗远超攻击者成本的查询资源。公开解析器背后还存在转发、共享出口和多上游拓扑，若不先解开这些关系，会重复计数并误判实际放大能力。
- **方法与贡献**：DaLens 构建可编程反应式权威服务器，把攻击交互模式编码进查询并动态响应；工具链先识别稳定开放解析器和共同递归出口，再以模块化任务测量不同自放大模式的消息放大因子。
- **方法示例**：探针向开放解析器查询受控域名，权威服务器根据查询状态返回会触发下一轮解析的记录；研究者能精确计数递归—权威往返，同时用出口集合判断多个前端地址是否其实属于同一解析器集群。
- **实验与证据**：2025 年 3、7、8 月三轮 IPv4 测量观察到 342 万个地址，筛得 307,397 个持续、响应正确的公开解析器。最终 276,399 个解析器对应 21,344 组递归出口；抽象后约有 2.9 万个放大器集群、11 万个确定性转发器和 18.9 万个多上游节点，超过 10% 的集群在部分模式下消息放大因子高于 100，个别接近 1,000。
- **局限与风险**：研究只测量开放解析器与受控域名，结论是保守下界，不能代表所有企业或运营商 DNS；集群抽象依赖可见出口，NAT、任播和策略变化仍会造成误差。详细可利用数据未公开，且测量按速率限制与协调披露执行。
- **实践关系**：解析器运营方应关闭不必要的公网递归、限制异常委派与循环行为，并按实际递归出口而非扫描 IP 做资产和补丁优先级；测量平台必须设置停止条件，避免自身成为放大器。
- **推荐理由**：它首次把 DNS 自放大从单个 PoC 扩展到经过去重的互联网规模基线，并公开讨论测量伦理和拓扑误差。

### 7. TIMESLICE-SANDWICH: A GPU Side-Channel Attack Exploiting Time-Sliced Scheduling

- **方向**：系统与硬件安全 / GPU 共享
- **关键词**：GPU、时分调度、侧信道、模型指纹、网站指纹
- **名词解释**：
  - **时分调度**：多个任务轮流占用同一 GPU，每个任务获得一小段连续执行时间。
  - **模型指纹**：从共享硬件上的时序或资源变化推断受害者正在运行的模型类型，而不读取模型文件。
- **单位与作者**：
  - Korea University：Hodong Kim、Gyeongsup Lim、Youngjoo Shin、Junbeom Hur
  - State University of New York at Binghamton：Seunghee Shin
- **出处与状态**：USENIX Security 2026｜接收
- **公开或更新时间**：2026-08-12 正式发表
- **原文链接**：[USENIX 官方页面](https://www.usenix.org/conference/usenixsecurity26/presentation/kim-hodong)、[正式论文集 PDF](https://www.usenix.org/system/files/usenixsecurity26-kim-hodong.pdf)
- **核心问题**：GPU 侧信道通常依赖缓存或内存争用，但标准的时分调度本身也泄露共置程序的运行时长。攻击者能否仅用自身 CUDA 事件和极小忙等内核，恢复受害者的 GPU 使用轨迹而不读取性能计数器？
- **方法与贡献**：TIMESLICE-SANDWICH 先测定时间片上界，再把攻击者内核放在受害者时间片前后，利用 CUDA Event 的延迟估计中间运行时长；得到的时间序列输入分类器，用于 DNN 架构和 GPU 加速网页指纹识别。
- **方法示例**：攻击者连续提交短忙等内核；当推理或网页渲染占用一个较长时间片时，两次事件之间出现稳定空隙。多层网络的时间片序列形成可区分的“条码”，无需与受害者共享内存。
- **实验与证据**：RTX 2080 Ti、3080、4090 覆盖 Turing、Ampere、Ada。20 个 ImageNet DNN 的平均 F1 为 94.40%；Alexa Top-200 网站识别在普通与 MPS 模式下 Top-1 分别为 92.11% 和 93.56%，Top-3 为 96.79% 和 97.38%。固定噪声下平均 F1 仍为 85.87%，变化噪声最低降至 50.16%。
- **局限与风险**：攻击需要原生 CUDA、与受害者共置且共享同一 GPU，浏览器 JavaScript 当前不可直接实施；只评估 NVIDIA 三代消费 GPU，AMD、Intel 与生产云调度器上的泛化未验证。噪声工作负载显著降低准确率。
- **实践关系**：高敏感 GPU 租户应使用 MIG 等空间隔离或独占设备；限制高精度 Event、固定或随机时间片只能部分缓解，仍需结合调度隔离和异常共置监控。
- **推荐理由**：它揭示了“没有缓存争用就没有 GPU 侧信道”的错误前提，对多租户推理平台的隔离设计有直接意义。

### 8. Silicon Heist: (Ransom) Attacks for AMD Cloud FPGAs via Privilege Escalation

- **方向**：系统与硬件安全 / 云 FPGA
- **关键词**：FPGA、权限提升、ICAP、JTAG、eFuse、硬件勒索
- **名词解释**：
  - **ICAP**：FPGA 芯片内部用于重新配置逻辑的接口，权限失控时可被用来替换正在运行的电路。
  - **eFuse**：芯片中一次性写入的熔丝位，常用于保存密钥或安全配置，误写通常难以恢复。
- **单位与作者**：
  - Max Planck Institute for Security and Privacy：Simon Klix、Felix Hahn、Maik Ender、Nils Albartus、Christof Paar
  - University of Massachusetts：Russell Tessier
- **出处与状态**：USENIX Security 2026｜接收
- **公开或更新时间**：2026-08-12 正式发表
- **原文链接**：[USENIX 官方页面](https://www.usenix.org/conference/usenixsecurity26/presentation/klix)、[正式论文集 PDF](https://www.usenix.org/system/files/usenixsecurity26-klix.pdf)
- **核心问题**：云 FPGA 只允许租户重配置动态区域，静态区域负责隔离管理接口。论文研究租户是否能从动态区访问内部配置端口，逐级获得底层 JTAG 和一次性 eFuse 控制，进而对云硬件造成持久破坏。
- **方法与贡献**：攻击从可实例化的 ICAP 原语开始，绕过云端设计检查并重配置局部 fabric，再启用 MASTER_JTAG 获得远程 JTAG 能力；作者枚举 eFuse 读写路径，提出把加密密钥或安全位写成不可恢复状态的硬件勒索威胁。
- **方法示例**：普通租户上传看似合规的 bitstream，在运行中经 ICAP 加载第二阶段配置并启用 JTAG；随后读取芯片身份或改写永久位。研究在真实云上停在破坏操作之前，只在本地 VCU118 验证 eFuse 控制。
- **实验与证据**：作者在 AWS EC2 F1/F2 的 AMD UltraScale+ FPGA 上演示从租户逻辑到 JTAG 的权限提升，并在本地板卡验证后续能力。AWS 确认可行性并在论文公开前缓解；AMD 发布设计公告，范围涉及 19 类设备。
- **局限与风险**：云端没有实际写入破坏性 eFuse，大规模勒索仍是威胁推演；F1/F2 的分区意味着损坏一个 SLR 不一定摧毁整块 FPGA，多租户横向影响也属假设。实验只覆盖 AMD Virtex UltraScale+，发现过程耗费数百小时，但已知链部署可很快。
- **实践关系**：云服务商必须把运行时局部重配置和配置原语纳入 bitstream 审核，隔离 ICAP/JTAG/eFuse 并监控二阶段加载；硬件厂商应在设备层强制租户域无法触达永久配置接口。
- **推荐理由**：论文展示了逻辑权限边界如何一路升级到不可逆硬件状态，也因真实云披露与厂商缓解而具有高实践价值。

### 9. StackWarp: Breaking AMD SEV-SNP Integrity via Deterministic Stack-Pointer Manipulation through the CPU’s Stack Engine

- **方向**：系统与硬件安全 / 机密计算
- **关键词**：AMD SEV-SNP、SMT、栈引擎、未文档化 MSR、完整性破坏
- **名词解释**：
  - **SEV-SNP**：AMD 用于保护虚拟机内存机密性和完整性的机密计算技术。
  - **SMT**：让同一物理核心同时运行多个硬件线程的机制，共享微架构状态也会带来跨线程攻击面。
- **单位与作者**：
  - CISPA Helmholtz Center for Information Security：Ruiyi Zhang、Tristan Hornetz、Daniel Weber、Fabian Thomas、Michael Schwarz
- **出处与状态**：USENIX Security 2026｜接收
- **公开或更新时间**：2026-08-12 正式发表
- **原文链接**：[USENIX 官方页面](https://www.usenix.org/conference/usenixsecurity26/presentation/zhang-ruiyi)、[正式论文集 PDF](https://www.usenix.org/system/files/usenixsecurity26-zhang-ruiyi.pdf)
- **核心问题**：SEV-SNP 旨在防止恶意 hypervisor 篡改来宾状态，但同一物理核的 SMT 线程仍共享部分 CPU 前端状态。论文研究未文档化栈引擎控制位在兄弟线程间不同步时，宿主能否确定性改变加密来宾的栈指针。
- **方法与贡献**：作者系统扫描 MSR 位，发现跨超线程共享的栈引擎控制位；在受害线程执行栈操作时关闭引擎会冻结隐藏偏移，重新开启时一次释放，从而注入可选方向和大小的栈指针位移，无需读取明文、注入来宾可见中断或预置 gadget。
- **方法示例**：恶意宿主在兄弟线程精确切换 MSR，使函数返回时栈指针跳回较早栈帧；同一原语可让认证函数复用“成功”状态，也可重排 ROP 所见的栈元素。
- **实验与证据**：原语在 Zen 1—5 多代处理器上成立，包括已完整打补丁的 Zen 5，测试位移最高达正负 640 字节。论文给出四条端到端链：用一份故障 RSA-2048 CRT 签名恢复私钥、绕过 OpenSSH 密码认证、绕过 sudo，以及在内核中构造 ROP 提权。
- **局限与风险**：威胁模型需要恶意或被攻陷的 hypervisor、SMT 共核和特权 MSR 控制，并依赖精确时序；实验在本地受控硬件完成，未证明公有云可稳定调度利用。论文未公开武器化代码；AMD 已发布可热加载微码缓解。
- **实践关系**：受影响平台在补丁不可确认时应关闭 SMT 运行机密虚拟机，并把微码版本纳入可信计算基线；长期修复需让栈引擎控制状态按线程隔离或在 CVM 运行时锁定。
- **推荐理由**：这项工作直接突破 SEV-SNP 的完整性承诺，并用密码、认证和内核三类利用说明其不是只可观察的微架构异常。

### 10. Not an A11y: How Android Accessibility Exposes Mobile AI Agents to Indirect Prompt Injection

- **方向**：移动与物联网安全 / 移动智能体
- **关键词**：Android 无障碍、移动智能体、间接提示注入、上下文边界、未授权操作
- **名词解释**：
  - **Android 无障碍服务**：可读取界面元素并执行点击等操作的高权限系统接口，移动智能体常借它控制应用。
  - **上下文边界**：区分用户指令、应用内容和系统元数据的信任分界；混在同一文本中时模型容易误判。
- **单位与作者**：
  - Radboud University：Rahul Deivasigamani、Faatin Alvi、Derqui Andrea、Kaushal Punjabi、Stjepan Picek
- **出处与状态**：arXiv｜预印
- **公开或更新时间**：2026-08-09 预印版本
- **原文链接**：[arXiv 原文](https://arxiv.org/abs/2608.08939)、[代码与材料](https://github.com/rahuldeiv/Not-An-A11y)
- **核心问题**：Android 移动智能体主要从 Accessibility 树读取文本、控件描述和应用状态，并辅以截图。攻击者可把指令放进通知、网页、输入字段、覆盖层或视觉上隐藏的无障碍元数据，让智能体把环境数据误当成用户意图。
- **方法与贡献**：作者建立 9 类攻击面的分类与测试基准，跨系统/运行时内容、应用与网页字段、隐藏 A11y 元数据和 AppCard 等载体，比较 MobileRun、Mobile-Use，不同模型、视觉开关与 Android 版本下的目标劫持、上下文漂移和未授权动作。
- **方法示例**：一个视觉上不可见但存在于 `contentDescription` 的文本要求智能体离开当前任务并打开设置读取 Build Number。人类用户看不到该指令，A11y 驱动的 Agent 却把它纳入规划并执行跨应用动作。
- **实验与证据**：在 Samsung 实体设备的 Android 13/16 上，每种配置运行 5 次。MobileRun 配 Gemma4:31B 的汇总攻击成功率为 0.822、配 Qwen3.6:35B 为 0.544；Mobile-Use 对应为 0.750 与 0.150。启用视觉输入会改变结果，但没有任何配置完全消除上下文漂移或未授权动作。
- **局限与风险**：该稿尚未经过同行评审；只覆盖 2 个框架、2 个模型、一个设备家族且每配置 5 次，结果是描述性比较而非总体估计。主要敏感动作是读取 Build Number，标签含人工判断，黑盒模型非确定性和设备残留状态也会影响结果；论文没有实测防御。
- **实践关系**：移动智能体应把 A11y、截图、通知和网页都标记为不可信观察，执行跨应用、读取隐私或改变设置前必须绑定用户原始目标并二次确认；隐藏元数据不能获得高于可见 UI 的指令优先级。
- **推荐理由**：它把移动智能体的感知层明确为安全边界，并用真实设备说明“无障碍可读”绝不等于“用户授权”。
